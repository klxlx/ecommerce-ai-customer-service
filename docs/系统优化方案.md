# 系统优化方案：三项兜底缺口

状态：方案稿，未改业务代码。  
基线：`feat/system-optimization`，架构说明见 `docs/系统架构与兜底机制.md`。

## 优先级

| 优先级 | 优化项 | 目标 | 预估 |
|---|---|---|---|
| P0 | 流式模型调用重试 | 流式失败可自动恢复，不重复吐字 | 0.5–1 人日 |
| P1 | tool 故障多级降级 | 能降级就不直接转人工，且不伪造事实 | 1.5–2 人日 |
| P2 | 任务中断断点回复 | 断线后同一回合可恢复，消息只落一次 | 3–4 人日 |

先做 P0：所有聊天都走流式，影响面最大、改动最小。  
P1 随后：把“工具一挂就人工”改成“先降级、再人工”。  
P2 最后：要动表、接口和前端，必须先把幂等做好。

---

## P0：流式模型调用重试

### 目标

- 流式模型在**首 token 之前**失败，自动重试，用户无感。
- 已吐出 token 后失败，不重复追加，改为**整段重生成 + `replace` 覆盖**。
- 知识回答本来就在缓冲区里，失败时可以直接整段重试，不需要 `replace`。
- 最终仍失败，保留现有 `PROVIDER_FAILURE_ANSWER` + 转人工工单。

### 方案

1. 在 `app/providers/chat.py` 增加 `stream_with_resilience`，复用 `ResiliencePolicy` 的预算、退避和熔断，但增加“是否已吐 token”的判断。
2. 首 token 前失败：按 `timeout / connection / rate_limit` 重试，默认 2 次、0.5s 退避；每次重新创建 SDK stream，不复用半截迭代器。
3. 首 token 后失败：抛 `ProviderStreamInterruptedError`（`retryable=False`），不透明重试，避免把同一段答案吐两遍。
4. `app/graph/nodes.py::_complete_answer` 分两条路径：
   - `sentinel` 路径（知识回答）：因为尚未向前端发 token，允许整段重试；重试仍失败再降级。
   - 普通流式路径：首 token 前由 wrapper 重试；已出 token 后失败，回退到 `chat.complete(messages)` 重新生成完整答案并返回。`app/api/routes/chat.py` 已有的 `replace` 逻辑会把气泡替换成完整答案，不追加第二条。
5. 最终失败仍由 `run_chat` 捕获 `ProviderError`，写 `PROVIDER_FAILURE_ANSWER`、`provider_failure` 证据和工单，保持现有客户侧兜底。

### 代码落点

- `app/providers/chat.py`：新增流式重试包装、首 token 标记、`ProviderStreamInterruptedError`。
- `app/core/errors.py`：新增 `stream_interrupted` 错误类别。
- `app/graph/nodes.py::_complete_answer`：缓冲路径与普通流式路径分开处理。
- `app/api/routes/chat.py::stream_message`：复用已有 `replace`，不新增事件类型。
- `tests/unit/test_provider_resilience.py`、`tests/unit/test_stream_buffer.py`、`tests/integration/test_chat_api.py`：补首 token 重试、半截失败替换、预算耗尽。

### 验收

- mock provider 首 token 前失败 2 次、第 3 次成功：前端只看到一份完整答案。
- mock provider 吐 3 个 token 后失败：前端收到 `replace`，最终气泡只有一份完整答案，没有重复前缀。
- 知识回答缓冲路径失败：重试后正常输出；仍失败则固定话术 + 工单。
- 总预算 60s 内不出现无限重试；指标能看到 `provider.stream_retry.total`、`provider.stream_partial.total`。

### 边界

- 不做 token 级断点续传。流式已吐出的半截内容不拼回模型上下文，避免重复和语义漂移。
- 不在 `stream` 内部无限重试；仍受 `CHAT_TOTAL_BUDGET_SECONDS` 约束。

## P1：tool 故障多级降级

### 目标

把当前“正常返回 / 安全话术 + 人工”两级，补成四级：

1. 正常调用。
2. 内部降级（跳过重排、走关键词召回）。
3. 对外降级（明确“查询暂不可用”，给自助入口）。
4. 安全兜底（知识缺口 / 人工工单）。

原则：**不伪造订单状态、价格、库存、售后进度。** 没有安全备用源的工具，就明确降级，不拿旧数据冒充实时事实。

### 方案

#### 1. RAG 三级降级

- L0：embedding → vector recall → rerank → parent expansion。
- L1：rerank 失败 → 直接用 vector score 排序，跳过重排，标记 `retrieval_mode=vector_only`。
- L2：embedding 或 vector recall 失败 → 关键词召回。新增 `rag_repo.keyword_recall`，用查询 2-gram 词项对已发布 child/parent 内容做 `ILIKE` 召回；不新增 pg_trgm 依赖，先保证可用。
- L3：仍无结果 → 现有 `knowledge_gap` + 安全话术 + 工单。

把 `retrieval_mode` 写入 `tool_evidence`，便于区分“没检索到”和“检索服务降级”。

#### 2. 业务工具对外降级

- 商品价格/库存、订单/物流、售后查询异常时，不再统一返回 `KNOWLEDGE_GAP_REPLY`。
- 新增 `TOOL_UNAVAILABLE_REPLY`：
  - 订单：提示“订单查询暂时不可用，可在订单详情页查看；需要我转人工吗？”
  - 售后：提示“售后查询暂时不可用，可在售后页面查看；需要我转人工吗？”
  - 商品：提示“价格/库存查询暂时不可用，请以商品详情页为准；需要我转人工吗？”
- 仍写 `tool_evidence`：`tool`、`degraded_reason`、`retrieval_mode`、`query_error`，保留审计。
- 工单仍可创建，但话术不再伪装成“知识没找到”。

#### 3. 工具级保护

- 新增 `app/core/tool_resilience.py`：
  - 只包装只读工具（商品、订单、售后、知识）。
  - 单工具超时；连续 3 次失败熔断 30s；熔断时直接返回 `unavailable`，不再打 DB。
  - 不做写操作自动重试：退换货提交、退款受理等不进入该包装。
- 指标：`tool.call.total`、`tool.degraded.total`、`tool.circuit_open.total`。

#### 4. 保留的 fail-open

- FAQ 缓存失败：跳过缓存继续主链路。
- 哨兵失败：fail open。
- 天气失败：返回天气不可用，不影响业务。

### 代码落点

- `app/rag/retriever.py`：拆 `retrieve_parent_context` 的 L0/L1/L2；新增 `retrieval_mode`。
- `app/db/repositories/rag.py`：新增 `keyword_recall`。
- `app/core/tool_resilience.py`：只读工具包装与熔断。
- `app/graph/nodes.py`：`catalog_node`、`order_node`、`after_sale_node` 改用 `TOOL_UNAVAILABLE_REPLY`。
- `app/services/chat.py`：区分 `tool_failure` 与 `knowledge_gap` 的工单证据。
- 测试：停掉 rerank / embedding、mock 关键词召回、DB 查询异常、熔断打开。

### 验收

- rerank 超时：知识回答仍能返回 vector-only 结果，不直接转人工。
- embedding 超时：关键词召回有结果则回答；无结果才知识缺口。
- 订单查询异常：返回“查询暂不可用 + 自助入口”，不返回“找不到知识”，不编造订单状态。
- 连续失败触发熔断后，后续请求快速失败，不再压 DB。
- 所有降级都带 `tool_evidence`，管理端日志可追溯。

### 边界

- 不缓存订单、售后、价格、库存的旧值来冒充实时结果。
- 不把写操作纳入自动重试；写操作失败必须让用户重新确认。

## P2：任务中断断点回复

### 目标

- 客户端断线、SSE 中断、页面刷新后，同一回合可以继续完成。
- 同一条用户消息只落一次，同一条 assistant 消息只落一次。
- 断点恢复优先“重生成 + 替换”，不做 token 级拼接。
- 写操作（退换货提交、退款受理）不自动重放，必须重新确认。

### 为什么不直接用 LangGraph checkpointer

当前 `AgentState` 里混了 `session`、`chat`、`providers`、`agents`、`stream` 等运行时依赖，直接序列化不安全。  
P2 先用独立的 `chat_turns` 存可恢复字段；等运行态依赖从 `AgentState` 拆出去，再评估接 `AsyncPostgresSaver`。

### 数据模型

新增迁移 `0012_chat_turns.py`：

```text
chat_turns
- id
- conversation_id
- user_id
- client_turn_id        # 前端 UUID，唯一键：conversation_id + client_turn_id
- user_message_id
- assistant_message_id
- status                # running | completed | interrupted | failed
- intent
- slots_json
- sources_json
- tool_evidence_json
- after_sale_context_json
- handoff_json
- partial_answer
- last_node
- error_code
- resume_count
- lease_expires_at
- created_at / updated_at
```

### 接口

- `MessageCreate` 增加 `client_turn_id`（可选 UUID）和 `resume`（默认 false）。
- `ChatResponse` 增加 `turn_id`、`resumed`。
- `POST /messages/stream`：
  - 新 turn：创建 `chat_turns`，写 user 消息，正常执行。
  - 已 completed：直接回放最终答案和 `done`，不重新生成。
  - interrupted/stale running：加载 checkpoint，恢复执行。
  - 并发 resume：用 `client_turn_id` 唯一键 + 行锁，保证只有一个执行者。

### 检查点

- `run_chat` 进入时创建/读取 turn。
- `route` 后保存 `intent`、`slots`。
- 工具节点后保存 `sources`、`tool_evidence`、`after_sale_context`。
- `_complete_answer` 每 100–200 字符或每 1 秒更新 `partial_answer`、`last_node`。
- 捕获 `CancelledError` 时，用独立 session 以 shield 方式写 `status=interrupted` 和 partial，再向上抛。

### 恢复策略

- 已有完整工具事实：跳过工具，直接重新生成回答。
- 工具未完成：只重跑只读工具；写操作不自动重跑。
- 回答已生成一半：用同一 `intent + slots + tool_evidence + sources` 重新生成完整答案，发 `replace` 覆盖气泡。
- 原 turn 已完成但客户端没收到 `done`：直接返回已存 assistant 消息，不重复生成。

### 前端

- `sendMessageStream` 增加 `turnId`、`resume` 参数。
- `CustomerApp` 首次发送生成 UUID；流中断且未收到 `done` 时，自动用同一 `turnId` 重试一次。
- 重试期间显示“正在恢复回答”；成功后 `replace` 当前气泡；再次失败才提示手动重试。
- 用户消息气泡不重复创建，assistant 气泡不追加第二条。

### 清理与安全

- `lease_expires_at` 默认 90s；超时 running 视为 interrupted。
- 恢复窗口 10 分钟；超时后标记 failed，要求用户重新发送。
- 只允许会话所有者 resume；不做跨会话恢复。
- 指标：`turn.checkpoint.write`、`turn.resume.attempt`、`turn.resume.success`、`turn.interrupted`。

### 验收

- 流式输出到 50% 时断开，前端自动重连：最终只有一条 user 消息、一条 assistant 消息，答案完整。
- 断开后刷新页面再恢复：同一 `client_turn_id` 不新建消息，能从 checkpoint 继续。
- 已完成 turn 重复 resume：直接回放，不重新调用模型。
- 退换货提交中断：不自动重放，提示用户重新确认。
- 两个客户端同时 resume：只有一个执行，另一个拿到同一最终结果。

### 边界

- 不做 token 级 SSE 重放；用 `replace` 保证最终一致。
- 不自动恢复写操作；避免重复退款/重复退换货。

---

## 建议实施顺序

1. **P0 流式重试**：先补首 token 前重试和半截失败 `replace`，这是当前最影响体验的缺口。
2. **P1 RAG 降级**：先做 rerank bypass 和关键词召回，再改业务工具话术与熔断。
3. **P2 断点回复**：先落 `chat_turns` 和幂等，再做前端自动重连；不要先做前端、后补幂等。

三项都不要一次性全上。每项单独提交、单独回归，P0/P1 可以共用现有测试库；P2 需要新迁移和前端联调。
