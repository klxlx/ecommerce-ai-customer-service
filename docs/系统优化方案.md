# 系统优化方案：三项兜底缺口

状态：P0 已实施；P1/P2 仍为方案稿，业务代码未改。

基线：`feat/system-optimization`。

目标：把图里标出的三项缺口补成可实现、可验证、可回滚的机制，不做“看起来有、实际不可靠”的兜底。

## 0. 优先级

| 缺口 | 优先级 | 工作量 | 目标 |
|---|---|---|---|
| 流式模型调用无重试 | P0 | S（0.5–1 人日） | 首 token 前失败可自动重试；重试耗尽可降级到非流式 |
| 工具无备用源 | P1 | M（1.5–2 人日） | 工具级超时/熔断 + 分工具降级链，不伪造事实 |
| 任务无断点 | P2 | L（4–6 人日） | turn 级断点重连与事件回放，不是 token 级续写 |

落地顺序：**P0 → P1 → P2**。三项都加开关，默认逐步打开，出问题可按环境变量回滚。

## 1. 流式模型调用无重试（P0）

### 现状

- `chat.complete`、Embedding、Rerank 走 `execute_with_resilience`，有重试和熔断。
- `chat.stream` 直接读 SDK 流，只有单次空闲超时和总预算，没有自动重试。
- 流式失败后由 `run_chat` 捕获，返回 `PROVIDER_FAILURE_ANSWER`；如果已经输出过 token，SSE 用 `replace` 覆盖气泡。

### 方案

把“可重试边界”定在**客户可见首 token 之前**：

1. 在 `app/core/resilience.py` 增加 `execute_stream_with_resilience`，复用现有 `ResiliencePolicy`：
   - 默认 2 次重试、0.5s 固定退避；
   - 单次超时 30s，总预算 60s，退避也计入总预算；
   - 只重试 `timeout`、`connection`、`rate_limit`；
   - 熔断仍按 provider 连续 3 次最终失败、30s 冷却。
2. 在 `app/graph/nodes.py::_complete_answer` 包一层流式消费：
   - 记录 `visible_token_emitted`：只统计已通过 `sink` 发给前端的 token，sentinel 缓冲不算；
   - 未发出可见 token 时，允许整段重试；
   - 已发出可见 token 后，不重试原流，避免把同一段答案吐两遍；改为执行第 3 步的 `complete` 兜底；
   - 知识回答走 sentinel 缓冲，缓冲阶段没有可见 token，因此也可以整段重试。
3. 已出 token 后或流式重试耗尽，降级到 `chat.complete` 一次：
   - `complete` 继续走现有重试；
   - 成功后返回完整答案；SSE 侧对比已发送内容，用 `replace` 覆盖气泡，不追加第二条；
   - 如果原本没有可见 token，则按 `_answer_chunks` 分块写给前端，用户体验仍是流式；
   - `complete` 也失败则走 `PROVIDER_FAILURE_ANSWER` + 工单。
4. 新增 `ProviderStreamInterruptedError`（`stream_interrupted`，`retryable=False`），用来区分“首 token 前可重试”和“已出 token 后只能替换”。
5. 增加指标：
   - `provider.stream.attempt.total`
   - `provider.stream.retry.total`
   - `provider.stream.fallback_complete.total`
   - `provider.stream.partial_fail.total`
6. 前端不改协议；已有 `replace` 和 `done` 足够覆盖“已输出后失败”的场景。

### 实施状态

已落地 `execute_stream_with_resilience`、`ProviderStreamInterruptedError` 和两个开关；`_complete_answer` 记录可见 token、首 token 前重试、已出 token 后走 `complete` 替换。新增单测覆盖重试、缓冲重试、替换、兜底失败和开关关闭；SSE 集成测试覆盖“重试后只输出一条答案”和“半截后 `replace`”。

### 改动点

- `app/core/resilience.py`
- `app/core/errors.py`（新增 `ProviderStreamInterruptedError`）
- `app/providers/chat.py`
- `app/graph/nodes.py::_complete_answer`
- `app/core/config.py`、`.env.example`
- `app/services/chat.py`（把 settings/metrics 注入图状态）
- `tests/unit/test_provider_resilience.py`、`test_stream_buffer.py`
- `tests/integration/test_chat_api.py`

### 验收

- 第一次流式调用在首 token 前抛 `ProviderTimeoutError`，第二次成功：只产生一条 assistant 消息、一次 `done`，不重复用户消息。
- 首 token 前连续失败：降级 `chat.complete` 成功，前端收到分块 token + `done`。
- 已输出第 1 个 token 后失败：不重试原流；`complete` 成功时收到 `replace` + `done`，最终只有一条完整答案；`complete` 也失败时才收到固定失败话术 + 工单。
- 总预算耗尽时不会无限重试，指标有 `provider.stream.partial_fail.total`。
- 开关：`STREAM_RETRY_ENABLED`，关闭后行为与当前完全一致；`STREAM_PARTIAL_FALLBACK_ENABLED` 控制已出 token 后是否走 `complete` 替换。

### 不做

- **不做半截续写**。模型 API 无状态，无法保证从某个 token 继续生成后语义一致；已输出后的正确做法是 `replace`，不是拼接。

## 2. 工具故障多级降级（P1）

### 现状

- 知识检索、商品、订单、售后工具异常时，节点直接 `except Exception`，返回 `KNOWLEDGE_GAP_REPLY` + 人工工单。
- 没有工具级超时、重试、熔断；没有备用数据源；没有统一的降级证据字段。

### 方案

新增工具执行层 `app/tools/runtime.py`，**只读工具**统一走 `execute_tool`；写操作不进入该包装：

- `ToolPolicy`：`timeout_seconds`、`max_retries`、`circuit_threshold`、`cooldown_seconds`、`fallback_chain`、`stale_allowed`。
- 超时用 `asyncio.timeout`；只对连接类/临时性异常重试 1 次，业务校验错误不重试。
- 只读工具使用独立 session/连接或保存点，避免超时后污染当前会话事务。
- 每个工具独立熔断，避免一个工具拖垮整轮对话。
- 统一 `tool_evidence`：
  ```json
  {
    "tool": "catalog",
    "status": "ok|degraded|failed",
    "source": "db|cache|faq|keyword|static|none",
    "fallback_level": 0,
    "stale": false,
    "latency_ms": 42
  }
  ```
- 指标：`tool.call.total`、`tool.failure.total`、`tool.degraded.total`、`tool.circuit_open.total`、`tool.latency_ms`。

### RAG 内部降级链

- L0：embedding → vector recall → rerank → parent expansion。
- L1：rerank 失败/超时 → 跳过重排，直接用 vector score 排序，标记 `retrieval_mode=vector_only`。
- L2：embedding 或 vector recall 失败 → 先查 FAQ curated 语义缓存（阈值 0.92），无命中再走 2-gram `ILIKE` 关键词召回。
- L3：仍无结果 → `knowledge_gap` + 安全话术 + 工单。

`retrieval_mode` 写入 `tool_evidence`，能区分“没检索到”和“检索服务降级”。

### 对外话术降级

商品、订单、售后查询异常时，不再统一返回 `KNOWLEDGE_GAP_REPLY`，改用 `TOOL_UNAVAILABLE_REPLY`：

- 订单：提示“订单查询暂时不可用，可在订单详情页查看；需要我转人工吗？”
- 售后：提示“售后查询暂时不可用，可在售后页面查看；需要我转人工吗？”
- 商品：提示“价格/库存查询暂时不可用，请以商品详情页为准；需要我转人工吗？”

仍然写 `tool_evidence` 和工单，但不把“工具查询失败”伪装成“知识没找到”。

### 分工具降级矩阵

| 工具 | 主源 | L1 备用 | L2 兜底 | 约束 |
|---|---|---|---|---|
| 商品价格/库存 | PostgreSQL | 30s 进程内读缓存，标记 `stale=true` | 安全话术 + 人工 | 缓存只用于短期读，不写回 |
| 知识检索 | pgvector RAG | rerank 失败→vector_only；embedding 失败→FAQ curated 缓存 / 2-gram 关键词召回 | `knowledge_gap` + 工单 | 必须带来源，不能编答案 |
| 订单/物流 | PostgreSQL | **不缓存** | 查询不可用 + 人工 | 订单状态变化快，禁止用旧事实 |
| 售后查询 | PostgreSQL | **不缓存** | `query_error` + 人工 | 金额/状态敏感，禁止用旧事实 |
| 天气 | MCP | 无 | 天气暂不可用 | 不影响主业务 |
| 工单/退换货写入 | PostgreSQL 事务 | 不适用 | 错误返回 + 重试 | 写入必须幂等，不能缓存替代 |

原则：**能安全降级的才降级，不能安全降级的直接转人工。** 订单、售后、退款金额这类事实不允许用缓存冒充实时结果。

### 改动点

- 新增 `app/tools/runtime.py`
- `app/rag/retriever.py`（rerank bypass / FAQ / keyword 降级）
- `app/db/repositories/rag.py`（新增 2-gram `ILIKE` 关键词召回）
- `app/tools/catalog.py`、`orders.py`、`after_sales.py`、`knowledge.py`
- `app/graph/nodes.py` 的 `knowledge_node`、`catalog_node`、`order_node`、`after_sale_node`
- `app/services/chat.py` 的 `tool_evidence` 记录、`TOOL_UNAVAILABLE_REPLY` 与指标
- `tests/unit/test_tool_runtime.py`、`tests/integration/test_tool_degradation.py`、`tests/unit/test_retrieval_fallback.py`

### 验收

- 注入 catalog 超时：返回 `status=degraded`、`source=cache`、`stale=true`，回答带“以下单页为准”，不崩溃。
- 注入 rerank 超时：知识回答仍能返回 `retrieval_mode=vector_only`，不直接转人工。
- 注入 embedding 超时：先查 FAQ curated 缓存，再走关键词召回；有结果则回答，无结果才 `knowledge_gap` + 工单。
- 注入 order/after_sale 超时：返回 `status=failed`、`source=none` 和 `TOOL_UNAVAILABLE_REPLY`；测试断言绝不返回缓存订单/售后事实。
- 连续失败达到阈值后熔断打开，冷却后自动半开恢复。
- 所有失败路径都有 `tool_evidence`，管理端日志可审计。
- 开关：`TOOL_FALLBACK_ENABLED`、`RAG_DEGRADED_RECALL_ENABLED`。

### 不做

- 不做订单/售后状态的 stale cache。
- 不做“工具失败后仍返回编造事实”的降级。
- 不在本轮引入 Redis；catalog 先用进程内 30s TTL，多 worker 后再迁共享缓存。

## 3. 任务中断断点回复（P2）

### 现状

- 没有 checkpoint、断点续跑、自动续答。
- 客户端断开时 SSE 路由会取消当前 task；前端没有 `done` 就抛“流式响应中断，请重试”，回拉历史后由用户重发。
- 已输出 token 没有服务端缓冲，重连无法补齐。

### 方案：turn 级断点回复，不是 token 级续写

核心是把“生成任务”和“HTTP 连接”解耦：

1. 新增 `chat_turns` 表：
   - `id`、`conversation_id`、`user_message_id`、`assistant_message_id`
   - `client_request_id`（幂等键，唯一）
   - `status`：`pending / running / completed / failed / interrupted`
   - `intent`、`slots`、`partial_answer`、`last_event_id`
   - `attempt_no`、`error_code`、`lease_until`、`created_at`、`updated_at`
2. 新增 `chat_turn_events` 表：
   - `turn_id`、`seq`、`event_type`（`token / replace / done / error`）、`payload`、`created_at`
   - 唯一索引 `(turn_id, seq)`；按 `seq` 回放。
3. 新增 `app/services/turns.py`：
   - `TurnManager` 负责创建 turn、启动后台生成任务、写事件、心跳、TTL 清理。
   - 生成 task 必须由 `TurnManager` 持有；不能继续绑在 `stream_message` 的 `finally` 上取消。
   - 后台任务用 `app.state.session_factory` 建独立 session，不能复用请求级 session。
   - 客户端断开时**不立刻取消生成**；解绑消费者，任务继续跑，事件写入缓冲。
   - token 事件按 200ms 或 20 条批量落库，内存保留最近事件；避免每个 token 一次 DB 写。
   - 超过 `TURN_TTL_SECONDS`（默认 300s）仍未完成，标记 `interrupted` 并取消。
4. SSE 协议升级：
   - `POST /messages/stream` 接受 `Idempotency-Key`，首个事件返回 `turn`，包含 `turn_id`。
   - 每个 SSE 事件带 `id: <seq>`，支持浏览器 `Last-Event-ID`。
   - 新增 `GET /api/conversations/{id}/turns/{turn_id}/stream?last_event_id=N` 用于重连。
5. 行为矩阵：
   - `running`：从 `last_event_id+1` 回放，再接着推实时事件。
   - `completed`：回放全部事件，最后补 `done`，不重新生成。
   - `failed`：返回 `error`，前端提示重试；重试使用同一 `client_request_id`，不重复写 user 消息。
   - 并发 resume：`client_request_id` 唯一键 + `SELECT FOR UPDATE` / advisory lock，保证只有一个生成 task。
   - 服务重启：把 `running` 标记为 `interrupted`；客户端可重新发起，不做跨进程续跑。
6. 前端 `sendMessageStream`：
   - 保存 `turn_id` 和最后收到的 `seq`；
   - 断线后自动重连 2 次（指数退避 0.5s / 1s）；
   - 重连成功继续追加 token，失败才显示“请重试”；
   - 页面刷新后可通过 `turn_id` 恢复当前会话的最后一条未完成回复。

### 分两步落地

- **2A（先做，2–3 人日）**：`chat_turns` + `Idempotency-Key` + 同一 turn 重试；断线后用 `replace` 返回完整答案，不做事件回放。先保证“消息不重复、回合能完成”。
- **2B（再做，2–3 人日）**：`chat_turn_events` + `Last-Event-ID` 回放；断线后从 `seq` 继续，不重复已显示的 token。

如果排期紧，先上 2A；2B 是体验增强，不是正确性前提。

### 改动点

- `app/db/models.py`、`app/db/repositories/chat.py`
- 新增 `migrations/versions/0012_chat_turns.py`
- 新增 `app/services/turns.py`
- `app/api/routes/chat.py::stream_message`
- `frontend/src/api/chat.ts`、`frontend/src/routes/customer/CustomerApp.tsx`
- `tests/integration/test_chat_resume.py`、`tests/unit/test_turn_events.py`

### 验收

- 客户端在第 5 个 token 后断开，带 `last_event_id=5` 重连：收到第 6 个 token 到 `done`，不重复第 1–5 个 token。
- 同一 `Idempotency-Key` 重发两次：`chat_messages` 只有一条 user、一条 assistant。
- `completed` turn 重放：只返回历史事件和 `done`，不重新调用模型。
- 服务重启后 `running` turn 变为 `interrupted`，客户端收到明确错误，不假装续跑成功。
- `TURN_TTL_SECONDS` 到期后有清理任务，事件表不会无限增长。
- 开关：`TURN_RESUME_ENABLED`。

### 不做

- **不做 token 级模型状态续写**。当前模型 API 不暴露生成状态，无法保证从半句话继续后语义一致。
- 不做跨实例任务共享；当前是单进程，后续上多 worker 再引入 Redis/任务队列。
- 退换货、工单写入不做自动续跑，避免重复副作用；只做幂等拒绝。
