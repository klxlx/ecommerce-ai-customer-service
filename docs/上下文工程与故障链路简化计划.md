# 上下文工程与故障链路简化计划

状态：方案稿，待确认  
基线：`feat/system-optimization` @ `dfc0b0f`  
目标：只做“Prompt 上下文组装 + 粗粒度故障链路排查”，不做 L2 摘要、L3 用户画像、Checkpointer、数据库迁移和精确节点级追踪。

## 1. 范围

### 做

- 统一上下文组装：System、当前会话槽位、最近历史、结构化工具事实、当前用户输入。
- 控制上下文预算：按字符/轮数截断，优先保留系统规则、当前问题和当前工具事实。
- 工具结果结构化：订单、商品、售后分别输出紧凑中文事实，禁止把原始 JSON 塞进回答 Prompt。
- 故障链路：在 `AgentRun.trace` 记录粗粒度 `stage`、`status`、`error_code`、`related_tool`、`fc_fallback` 和 `path`。
- 工单关联：把 `trace_id` 写入工单 `evidence`，管理端从工单跳到运行日志。
- 运行日志展示：增加“链路/阶段/错误码”字段，管理员能看出大致是路由、检索、工具、回答、哨兵还是转人工出错。

### 不做

- L2 滚动摘要、L3 用户画像、跨会话长期记忆。
- LangGraph Checkpointer、任务断点恢复。
- 数据库迁移；本次只用现有 JSON 字段。
- 精确到每个节点的耗时、堆栈、重试次数。
- 写操作 Function Calling。
- 完整 Prompt 原文落库；只存上下文清单和长度。

## 2. 上下文工程

### 2.1 统一 Context Pack

新增 `app/context/`：

- `models.py`：`ContextPack`、`ContextBlock`、`ContextManifest`。
- `builder.py`：`build_context_pack(state, purpose)`。
- `formatters.py`：`format_tool_facts(tool_evidence)`。
- `budget.py`：字符预算和截断策略。

第一版 Context Pack 只有五块：

1. System Prompt：角色、安全红线、业务硬规则，永不截断。
2. 当前会话槽位：`order_no`、`query_scope`、`after_sale_action` 等，紧凑键值。
3. L1 最近历史：最近 6 轮，最多 12 条消息；按字符预算截断最旧消息。
4. 当前工具事实：结构化精简文本，不放原始 JSON。
5. 当前用户输入：永不截断。

预留 `summary` 和 `profile` 字段为空，但不接入 L2/L3，避免本次扩大范围。

### 2.2 事实优先级

Prompt 中明确写死：

```text
安全规则
> 当前工具事实
> 当前用户明确输入
> 当前会话槽位
> 最近历史
```

历史只能帮助理解指代，不能覆盖当前工具结果。静态 FAQ 仍走语义缓存，不作为动态订单事实。

### 2.3 预算

建议默认值：

```env
CONTEXT_ENGINE_ENABLED=0
CONTEXT_MAX_CHARS=6000
CONTEXT_HISTORY_TURNS=6
CONTEXT_HISTORY_MAX_CHARS=3000
CONTEXT_TOOL_FACTS_MAX_CHARS=1200
CONTEXT_SLOTS_MAX_CHARS=300
```

截断顺序：

1. 先丢最旧历史。
2. 再把工具事实压缩为关键字段。
3. 系统规则、当前用户输入不截断。
4. 超预算时记录 `context.truncated=true` 和丢弃条数，供排查。

### 2.4 工具事实格式

禁止：

```json
{"orders":[{"order_no":"ORD-7001","status":"已发货","items":[...]}]}
```

改成：

```text
订单 2 笔：
- ORD-7001：已发货，金额 99 元，商品 测试商品A
- ORD-7002：待发货，金额 100 元，商品 测试商品B
```

按工具分别定义：

- 订单：订单号、状态、金额、商品名、最新物流。
- 商品：SKU、名称、价格、库存。
- 售后：类型、状态、退款金额、申请时间。
- 知识：来源标题、页码、短摘要，不塞整段检索原文。

### 2.5 接入位置

优先接入三条链路：

- `build_answer_messages`：知识、订单、售后回答。
- `build_tool_planner_messages`：FC planner 只看到最近历史、槽位和当前问题。
- `build_router_messages`：路由只需要最近历史、槽位和当前问题，不注入工具事实。

`CONTEXT_ENGINE_ENABLED=0` 时保留现有 Prompt 行为，便于回滚。

## 3. 故障链路排查

### 3.1 粗粒度阶段

不记录精确节点，只记录阶段：

```text
route | retrieval | catalog | order | after_sale | answer | sentinel | handoff | cache
```

### 3.2 trace.diagnosis

在 `AgentRun.trace` 增加：

```json
{
  "diagnosis": {
    "stage": "order",
    "status": "failed",
    "error_code": "TOOL_FAILURE",
    "related_tool": "order",
    "fc_fallback": "tool_timeout",
    "path": ["route:order", "order:tool_failure", "handoff:internal"]
  }
}
```

错误码限定为稳定枚举：

- `TOOL_FAILURE`
- `PROVIDER_FAILURE`
- `KNOWLEDGE_EMPTY`
- `THRESHOLD_EXCEEDED`
- `SENTINEL_FLAGGED`
- `CLARIFICATION_LIMIT`
- `HANDOFF_LIMIT`
- `FC_FALLBACK`
- `CACHE_HIT`

只记录类别，不记录原始异常文本、数据库连接串或 Prompt 原文。

### 3.3 工单关联

- `HandoffTicket.evidence` 增加 `trace_id`。
- `AgentRun` 创建后回写该工单的 `evidence.trace_id`；工单复用时合并。
- 管理端工单详情增加“查看运行日志”入口，链接带 `conversation_id`。
- 运行日志项增加 `diagnosis_stage`、`diagnosis_code`、`trace_id`、`fc_fallback`。
- 日志表增加“链路”列，显示例如：`route → order → tool_failure → handoff`。

不新增表、不做数据库迁移。

### 3.4 管理端能看到什么

- 工单：摘要、槽位、工具证据、内部/人工类别、运行链路、trace_id。
- 运行日志：意图、工具、检索结果、售后状态、阶段、错误码、是否转人工。
- 不展示完整 Prompt、用户隐私字段或原始异常堆栈。

## 4. 实施拆分

### Phase 1：Context Pack（2–3 天）

- 新增 `app/context/` 四个模块。
- 定义 `ContextPack` 和 `ContextManifest`。
- 结构化工具事实格式化。
- 接入 `build_answer_messages`、`build_tool_planner_messages`、`build_router_messages`。
- 加开关和预算配置。
- 单测：顺序、预算、截断、无原始 JSON、事实优先级。

### Phase 2：粗粒度诊断（1–2 天）

- 在 `_persist_result` 生成 `trace.diagnosis` 和 `path`。
- 工单 `evidence` 回写 `trace_id`。
- 扩展 `OperationalLogItem` 和日志查询/序列化。
- 工单详情与日志页增加链路展示和跳转。
- 单测/集成测试：工具失败、Provider 失败、知识缺口、FC 回退、阈值、哨兵。

### Phase 3：验收与演示（1 天）

- 10 轮长对话：验证最近 6 轮 + 槽位仍能正确承接。
- 订单 FC：列表、详情、回退。
- 工具故障工单：从工单看到 `order → tool_failure → handoff`。
- 越权订单：不枚举、能显示 `TOOL_FAILURE` 或 `not_found` 路径。
- 回归：现有 207 单元 + 159 集成测试全绿。

总工作量：4–6 人日。

## 5. 验收门禁

- `CONTEXT_ENGINE_ENABLED=0` 时现有测试全绿。
- `CONTEXT_ENGINE_ENABLED=1` 时回答 Prompt 中不出现原始 JSON。
- 任意工具失败工单能在管理端看到大致链路，不需要查数据库。
- 工单详情能跳到对应会话的运行日志。
- 日志不泄露 Prompt 原文、数据库连接串、用户敏感字段。
- 10 轮对话不因窗口截断丢失当前订单号/售后类型。
- FC 回退时 `fc_fallback` 能在日志中看到。

## 6. 演示脚本

1. 先关闭 `CONTEXT_ENGINE_ENABLED`，问“我的订单有哪些”，展示原行为。
2. 打开开关，问同样问题，展示 Context Manifest：使用了哪些历史、槽位、工具事实。
3. 问“查 ORD-7001”，展示结构化工具事实和回答。
4. 制造一次订单工具失败，打开工单，展示 `route → order → tool_failure → handoff`。
5. 点“查看运行日志”，展示阶段、错误码和 trace_id。
6. 问“我要退款”，说明写操作仍走确定性流程，不进入 FC。

## 7. 风险与回滚

- Prompt 行为变化：`CONTEXT_ENGINE_ENABLED` 默认关闭，出问题直接关。
- 诊断是推断型链路，不保证精确节点；只用于快速定位大致阶段，不作为审计证据。
- 工单 `trace_id` 写在 JSON evidence，不迁移表；后续需要精确追踪再升级。
- 长对话仍受窗口限制；L2/L3 留到下一阶段，不在本次承诺。
