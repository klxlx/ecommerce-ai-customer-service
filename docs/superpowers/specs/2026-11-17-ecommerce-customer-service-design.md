## 1. 结论

本轮方案已对照 GitHub 参考项目重新审计，不再把“已有主链路”等同于“可交付”。
当前系统仍处于分步完善阶段，整体未达到交付完成标准。

已确认的推进顺序是：

1. `P0`：补齐售后只读事实链路、售后路由和确定性退款阈值规则。
2. `P1`：补齐顾客端及管理端的售后交互体验；移动端专项暂停。
3. `P2`：补齐登录防护、限流、依赖异常、状态建模和可观测性。
4. `P3`：补齐知识库添加、知识审计、日志查看筛选和运营闭环。

优先级固定为：**产品能力 > 交互体验 > 技术架构 > 交付完整度**。

本设计只授权开始 `P0`。`P1`、`P2`、`P3` 只记录方向和返工项，不在本阶段写生产代码。

## 2. 参考项目审计

参考仓库可访问，已检查其 README、设计文档、路由、专家节点、售后工具、
退款阈值代码、售后模型、种子数据和评测说明。参考项目值得借鉴的不是全部技术栈，
而是售后能力被拆成独立业务链路，并有代码级风控兜底。

### 2.2 明确不照搬

| 参考实现 | 不采纳原因 |
|---|---|
| MySQL + Milvus + Redis 三套新基础设施 | 当前 PostgreSQL + PGVector 已满足边界，新增栈只会扩大交付风险 |
| 公开注册接口 | 不符合当前仅提供预置账号的产品范围 |
| 只按订单号查询、不校验用户归属 | 存在跨用户枚举和越权风险 |
| 普通 top-k 文本切片直接回答 | 当前父子块 RAG、rerank、父块扩展更可靠 |
| 用提示词替代硬规则 | 模型可能“查到金额但不触发转人工” |
| 自动化测试覆盖较薄 | 当前项目必须保留真实 PostgreSQL 集成测试和异常路径测试 |

### 2.3 参考项目的已知缺陷

参考项目的代码兜底会从订单查询工具结果中读取“订单实付金额”，
只要金额超过阈值就强制转人工。该逻辑没有区分：

- 用户正在查询历史退款进度；
- 用户正在发起新的退款请求。

因此，一张历史退款金额超过阈值的订单，即使用户只想查询处理进度，
也可能被误转人工。当前项目必须只在“新的退款诉求”上应用阈值，
历史售后查询不得因历史退款金额触发人工。

异常是否能被运营人员看见。`P0` 只解决售后能力从无到有，不能据此宣布整体交付。

## 4. 修订后的技术方案

### 4.1 总体原则

- 动态业务事实只从 SQL 读取，不进入向量库。
- 订单和售后归属只从服务端认证用户派生，模型不能提供或覆盖 `user_id`。
- 金额阈值、订单状态限制和转人工条件由代码决定。
- 模型只负责意图分类和槽位提取；不能决定是否越权、是否能退款或是否超阈值。
- 工具异常对用户统一脱敏，内部细节只进入服务端日志，不进入用户回答。
- 交易规则从已提供的 PDF 中整理后进入知识库，但必须先审计旧知识，
  不得直接清空或重建。

### 4.2 P0：售后只读链路

#### 数据模型

新增 `after_sales` 表：

| 字段 | 类型 | 约束 |
|---|---|---|
| `id` | `Integer` | 主键 |
| `order_id` | `Integer` | 外键到 `orders.id`，`ON DELETE CASCADE`，建索引 |
| `service_type` | `String(20)` | 非空，示例：退款、退货、换货 |
| `status` | `String(32)` | 非空，示例：待审核、处理中、已完成 |
| `refund_amount` | `Numeric(12, 2)` | 可空；非退款类型可为空 |
| `reason` | `Text` | 非空，默认空字符串 |
| `created_at` | `DateTime(timezone=True)` | 非空 |
| `updated_at` | `DateTime(timezone=True)` | 非空 |

`after_sales` 不存 `user_id`。归属只通过
`after_sales.order_id -> orders.user_id` 推导，避免两份归属来源不一致。

ORM 字段语义必须与迁移一致。`0001_initial.py` 当前使用
`Base.metadata.create_all()`，新模型注册后，新建库执行 `0001` 时可能已经创建
`after_sales`。因此 `0002_after_sales.py` 必须使用 SQLAlchemy inspector
检查表和索引，不能无条件重复建表。

#### 事实接口

新增：

```python
lookup_after_sales(
    session: AsyncSession,
    user_id: int,
    order_no: str,
) -> list[AfterSaleFact] | None
```

返回值语义：

- `None`：订单不存在或不属于当前用户。两种情况必须不可区分。
- `[]`：订单属于当前用户，但没有售后记录。
- 非空列表：订单属于当前用户，并返回该订单的售后记录。

`user_id` 只能来自服务端认证态。节点不得接受模型槽位里的
`user_id`、`owner_id` 或同类字段覆盖认证用户。

#### 意图边界

| 用户表达 | 意图 | 行为 |
|---|---|---|
| “七天无理由退货规则是什么” | `policy_knowledge` | 检索交易规则知识 |
| “我的订单 ORD-1 退款到哪了” | `after_sale` | 校验归属并查询售后记录 |
| “我要退掉订单 ORD-1” | `after_sale` | 进入售后处理，不直接转人工 |
| “我要退款” | `after_sale` | 缺少订单号时先澄清，不直接转人工 |
| “转人工” | `handoff` | 直接创建人工工单 |

必须从 `_HANDOFF_PATTERN` 移除“我要退款”。售后政策咨询仍走
`policy_knowledge`，具体订单的退款、退货、换货查询或诉求走 `after_sale`。

#### 售后回答规则

1. 缺少订单号时重新询问订单号。
2. 订单不存在或无权访问时统一回复“未查询到该订单”，不暴露原因。
3. 自有订单无售后记录时如实说明，并建议从订单详情页查看或申请人工帮助。
4. 查询已有售后记录时展示服务类型、处理状态、退款金额、原因和申请时间。
5. 订单状态为“待发货”或“运输中”时，不得回答为可以直接办理退货退款；
   应给出拒收、签收后申请等限制性说明，并以实际平台流程为准。
6. `P0` 只读，不创建、不审批、不修改退款、退货、换货或售后状态。

#### 退款阈值

固定阈值：

```python
REFUND_REVIEW_THRESHOLD = Decimal("500.00")
```

规则：

- 只有新的退款诉求参与阈值判断。
- 用户明确给出新退款金额时使用该金额。
- 用户未给出新退款金额时使用订单实付金额。
- 金额严格大于 `500.00` 才转人工；等于 `500.00` 不因阈值转人工。
- 仅查询历史售后进度时，不因历史退款金额或订单金额转人工。
- 待发货/运输中限制与超阈值转人工可以同时成立；超阈值时优先安全转人工。

#### 异常和 trace

- 售后仓储或工具异常时，用户收到脱敏提示并转人工。
- 用户回答、trace 和工具日志不得包含数据库连接串、异常堆栈或原始内部错误。
- `tool_call_logs.tool_name` 对售后查询记录为 `after_sale`。
- `agent_runs.trace.tool_evidence` 至少记录：
  - 只读售后事实；
  - 订单状态；
  - 阈值是否应用、金额、阈值、是否超限；
  - 转人工原因。

### 4.3 P1：交互体验

- 顾客端展示售后记录、状态、金额和下一步指引。
- 管理端增加售后相关运营视图，但不得绕过 `P0` 的只读边界。
- 移动端专项暂停，不列入本轮验收。
- 所有异常和空状态必须有明确文案，不能只显示通用错误。

### 4.4 P2：稳定性与安全

- 登录失败次数、锁定窗口和限流策略落地。
- 聊天限流、依赖故障、模型超时和重试边界明确。
- 会话、工具、转人工和阈值触发指标可观测。
- 状态枚举和异常分类集中定义，避免文案、日志和业务规则各说各话。
- 真实提供商行为需要单独验证，不能用 Mock 结果代替。

### 4.5 P3：知识与运营

已提供的 10 份 PDF 是商品信息和交易规则的正式来源：

- 6 份华为手机用户指南；
- 4 份京东售后、退款和纠纷规则。

后续流程固定为：

1. 审计旧知识库来源、准确性、重复和时效性。
2. 只删除确认不严谨、重复或过时的内容，不直接清空。
3. 从 PDF 提取商品信息与交易规则。
4. 按静态知识边界进行父子块切分和向量化。
5. 管理端支持添加知识库内容并触发入库。
6. 管理端支持日志查看和筛选，至少覆盖意图、工具调用、检索和转人工。

价格、库存、订单、物流和售后状态仍只存 SQL，不进入知识库。
