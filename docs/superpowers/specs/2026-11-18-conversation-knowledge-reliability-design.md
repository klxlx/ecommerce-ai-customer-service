# 会话、知识入库与客服回复可靠性整改方案

更新日期：2026-11-18

## 1. 结论

当前问题不能合并成一次“清库”处理，需拆成四条独立工作线：

1. 测试直接使用运行环境，留下了会话、知识和工单数据。
2. 顾客端直接展示了数据库自增主键，所以出现“会话 #114”。
3. 知识入库失败同时存在“删除后不能恢复”和“向量接口拒绝文本”两类原因。
4. “适用范围”和“生效日期”目前要求人工填写，资料本身没有明确依据时容易被随意填写。

会话编号增长不代表有 114 个真实咨询。`Conversation.id` 是数据库自增主键，
删除会话采用软删除，历史记录仍占用编号。正确处理是停止向顾客展示数据库 ID，
不重置数据库序列，也不重排历史会话。

## 2. 目标与非目标

### 2.1 目标

- 自动化测试和验收脚本不再向正式运行库写入会话、知识或工单。
- 每次测试无论成功、失败还是中途异常，都清理本次创建的测试数据。
- 顾客端不再展示 `#编号`，改为展示会话标题；“智能客服”作为新会话默认标题。
- 已删除的同一知识可以安全恢复，不产生重复主文档。
- 大批量或异常文本触发向量接口失败时，可以定位原因并给出可读提示。
- 有明确原文依据时自动识别“适用范围”和“生效日期”，没有依据时不猜测。
- 移除无作用的服务概览遗留入口、路由和编号显示。
- 为客服回复建立稳定的意图、事实、知识、澄清和转人工规则。

### 2.2 非目标

- 不重置数据库主键序列。
- 不批量物理删除软删除会话和知识。
- 不直接清空现有知识库后重建。
- 不使用文件名或相似标题模糊合并知识，避免误覆盖正式资料。
- 不引入新的消息队列、搜索引擎或向量数据库。

## 3. 已确认现状

### 3.1 会话编号

- 顾客端在
  `frontend/src/routes/customer/CustomerApp.tsx`
  中直接显示 `conversationId`。
- 会话删除只写入 `deleted_at`，不会缩短主键序列。
- 近期连续测试会在正式库中持续创建新会话，导致编号不断增大。

### 3.2 测试污染

- 单元和集成测试已有独立 `cs_test` 数据库，并在测试后清表。
- Playwright 默认访问 `http://127.0.0.1:8000`，当前可能连接正式运行库。
- 顾客端和管理端浏览器验收会直接创建会话、消息、工单和知识，部分流程没有自动清理。
- `scripts/evaluate.py` 使用当前 `DATABASE_URL` 创建会话，也没有清理本次数据。

### 3.3 知识入库失败

已确认两类原因：

1. 文件来源键由文件内容 SHA-256 生成。同一文件删除后再次上传会命中同一个
   `source_key`，当前服务直接返回“该知识已删除，不能使用相同来源键恢复”。
   这类失败确实与之前的删除有关。
2. 最近部分失败为 `embedding:invalid_request`，属于向量服务拒绝请求，
   与知识删除无直接关系。需要检查单条文本长度、批次总量、控制字符和服务端错误正文。

因此不能把近期所有入库失败都归因于删除。应先保留明确错误分类，再分别修复。

### 3.4 自动元数据

- 数据库已有 `applicability` 和 `effective_date` 字段。
- 注册 PDF 可从 `data/knowledge/pdf_sources.json` 获得明确元数据。
- 普通文件预览目前不返回识别结果，管理端仍让人工填写两个字段。

### 3.5 服务概览

管理端主导航已经没有“服务概览”入口，旧地址会跳转到工单队列。
后续只需清理遗留路由、文案和测试引用，不重新引入该页面。

## 4. 总体设计

### 4.1 测试隔离与自动清理

所有浏览器验收和评估脚本必须遵守以下规则：

1. 启动前检查运行环境。未显式标记为测试环境时，禁止直接连接运行库。
2. Playwright 和服务端验收使用独立测试部署或专用测试账号。
3. 每次测试生成一个批次标识，只使用该批次标识归属测试数据。
4. 测试辅助层记录本次创建的会话、消息、知识、工单和 AgentRun ID。
5. `afterEach`、`afterAll` 或 `finally` 执行清理，不使用标题模糊删除。
6. 清理顺序从依赖数据到主数据，覆盖消息、AgentRun、工具日志、工单、
   会话以及本次创建的测试知识版本。
7. 进程被强制终止时，由测试环境启动前的全量重置兜底；正式库不依赖事后补偿。
8. 每次测试结束后校验测试账号残留数量为 0。

现有测试数据不自动批量删除。先做只读盘点，列出账号、时间、标题、软删除状态和关联记录；
确认属于验收数据的记录后，再按明确 ID 分批清理。

### 4.2 顾客端会话展示

- 顾客端顶部显示会话标题。
- 新会话没有标题时显示“智能客服”。
- 数据库 ID 只保留在 URL 和内部接口关联中，不在任何顾客界面展示。
- 管理端如需排查问题，使用独立诊断字段或脱敏标识，不复用顾客端编号。

### 4.3 知识恢复与去重

知识主文档以 `source_key` 保证唯一，内容版本以 `checksum` 区分。处理规则固定为：

| 当前状态 | 新提交内容 | 行为 |
|---|---|---|
| 未删除，摘要相同 | 相同 | 返回 `unchanged`，不新建版本 |
| 未删除，摘要不同 | 更新 | 创建新版本并发布，旧版本退休 |
| 已删除，摘要相同 | 恢复 | 复用原主文档和原版本，清除删除标记 |
| 已删除，摘要不同 | 更新并恢复 | 先成功发布新版本，再清除删除标记 |

关键约束：

- 清除 `deleted_at` 只能在向量生成和版本发布成功之后执行。
- 恢复失败时知识必须保持删除状态，不能在检索中意外出现。
- 编辑已有知识时始终携带原 `source_key`，不能按新内容重新计算来源键。
- 注册 PDF 使用注册表中的稳定来源标识。
- 同一文件精确重复上传按内容摘要识别；不同内容不按文件名静默覆盖。
- 入库全过程使用同一来源键的咨询锁，并增加并发重复上传测试。
- 版本号、当前版本和检索可见性在同一发布操作中完成。

### 4.4 向量入库稳定性

向量调用前增加统一文本预处理和边界控制：

- 清除零宽字符、不可见控制字符和异常空白。
- 对单条输入和单批总字符数设置保守上限。
- 超限文本在父块边界内拆分，不截断正文。
- 批次发生 `invalid_request` 时使用二分方式定位问题文本。
- 对明确的超时、限流和服务端瞬时错误执行有限重试。
- 对鉴权失败、内容非法和参数错误不做无意义重试。
- 保存脱敏后的服务端错误类型和安全摘要，不记录完整敏感正文。
- 管理端显示“单条文本过长”“批次过大”或“向量服务不可用”等可操作提示。

### 4.5 适用范围与生效日期自动识别

采用“只识别明确证据”的确定性规则，不使用模型猜测：

- 注册 PDF 的元数据优先于正文识别。
- 日期只识别“生效日期：某日”“自某日起施行/生效/执行”等明确表达。
- 发布日期只有在同段明确说明“自发布之日起生效”时才作为生效日期。
- 适用范围只识别“适用范围”章节、“适用于”“仅适用于”“仅限”等明确表达。
- 预览结果返回识别值和命中原文，管理端显示为自动识别依据。
- 最终入库时后端根据最终 Markdown 重新识别，不信任前端传值。
- 管理端删除两个手工输入控件，只展示识别成功的只读标签。
- 没有明确依据时不显示这两个字段，也不要求填写。
- 数据库字段保留，供检索、审计和现有资料继续使用。

如果代表性资料验收命中率不足，管理端直接隐藏整个自动元数据区域，
而不是保留一个无法可靠填写的表单。

### 4.6 服务概览清理

- 删除 `/admin/overview` 的遗留路由和跳转兼容。
- 删除残留导航、标题、空页面文案和编号组件。
- 更新测试，验证旧地址不再显示任何服务概览或会话编号内容。

### 4.7 客服回复主链路

知识入库稳定后，客服回复按以下固定顺序执行：

1. 识别问候、商品咨询、价格库存、政策知识、订单物流、售后、转人工和闲聊。
2. 动态事实只查订单、物流和售后数据库；静态政策只查知识库。
3. 缺少订单号、商品名或问题类型时，只追问当前最关键的缺失信息。
4. 有可靠证据时先给结论，再给下一步操作；政策和商品答案附来源。
5. 没有可靠知识时不编造，统一说明暂时无法确认并提供转人工选项。
6. 工具失败、越权、高风险退款和用户明确要求时进入转人工。
7. 同一会话保持槽位和已澄清信息，避免重复询问。

回复验收至少覆盖：问候、商品价格、政策咨询、订单物流、无售后记录、
普通退款、超阈值退款、知识未命中、工具异常和转人工。

## 5. 数据清理与发布顺序

### 5.1 现有数据

1. 导出会话、知识、工单和任务统计，不修改数据库。
2. 标记测试账号、验收批次和无法确认归属的数据。
3. 只清理已确认的测试记录 ID。
4. 对软删除知识做重复来源审计，不按 `deleted_at` 直接批量物理删除。
5. 清理前后对账主文档、版本、父块、分块和检索可见数量。

### 5.2 实施顺序

| 阶段 | 内容 | 完成标志 |
|---|---|---|
| P0 | 冻结测试污染，停止展示会话编号 | 新测试不再写运行库，页面不再出现 `#id` |
| P1 | 修复知识恢复、去重和向量失败 | 删除后重传可恢复，重复上传不新增版本 |
| P2 | 客服回复规则和异常兜底 | 十类核心对话按固定规则通过验收 |
| P3 | 自动识别元数据，清理服务概览 | 有依据自动显示，无依据不显示手工项 |
| P4 | 经确认后清理历史测试数据 | 正式数据不受影响，残留测试数据为 0 |

## 6. 验收标准

- Playwright 成功、失败和异常退出后，测试环境残留会话为 0。
- 清理逻辑只删除本次测试或专用测试账号数据，真实会话数量保持不变。
- 顾客端顶部不再出现 `#编号`。
- 同一知识精确重复提交返回 `unchanged`，主文档和版本数量不增加。
- 删除后重新上传相同文件可以恢复，不再返回 409。
- 删除后提交不同内容时，发布成功才恢复可见；发布失败仍保持删除。
- 向量批次过大时能自动拆分或返回明确的文本定位信息。
- 明确写有生效日期和适用范围的资料能自动带出并显示依据。
- 没有明确依据时不显示手填框，也不生成猜测值。
- `/admin/overview` 不再保留入口、内容或编号显示。
- 客服回复在知识未命中、工具异常和超阈值退款时不会编造或跳过转人工。

## 7. 首轮实施边界

首轮只处理 P0 和 P1，并用只读方式完成现有数据盘点。
在用户确认清理清单前，不删除历史测试会话或知识，不重置任何编号。
