## A1. 退货按钮条件修复

### 现状

`app/services/chat.py::_persist_result` 只在同时满足以下条件时注入
`return_request` 按钮：

- `intent == "after_sale"`
- 本轮没有 `handoff`
- **本轮用户原话包含“退货 / 换货 / 退换”**

会话 96 中，消息 466 用户只回复订单号，因此 `actions=None`；消息 470 说“打开退货窗口”，
才出现按钮。售后上下文本身没有触发按钮。

### 建议方案

- 按钮判断从“本轮字符串”改为“售后动作 + 售后上下文”：
  - `after_sale_action == "new_request"` 时保留按钮；
  - 或 `after_sale_context` 明确表示新的退换货请求时保留按钮；
  - 仍排除 `handoff`、售后进度查询、退货政策问答和工单上限场景。
- 保留“本轮原话含退货词”作为兜底条件，避免改动后误给政策问答加按钮。
- 不改数据库，不改前端协议。

### 验收

- “我要退货” → 追问订单号 → 用户只回订单号：仍然有“申请退换货”按钮。
- “退货进度 / 退货政策 / 多久到账” → 不出现按钮。
- 已转人工或工单上限 → 不出现按钮。
- 补 2–3 条回归测试，现有 224 单测和 160 集成不回退。

## A3. 工具 / 检索多级降级

### 现状

- `app/tools/runtime.py` 已有超时、一次重试、每工具熔断和 `tool_evidence`，但只被订单 FC 的
  `tool_planner` 使用。
- 确定性节点 `knowledge_node`、`catalog_node`、`order_node`、`after_sale_node` 仍是
  `except Exception` 后直接返回 `KNOWLEDGE_GAP_REPLY` + 工单。
- `app/rag/retriever.py` 直接执行 embedding → vector recall → rerank，没有
  `vector_only`、FAQ 或关键词降级。
- 订单、售后查询异常没有独立的“查询暂不可用”话术。

### 建议分两步

**A3.1 工具运行时覆盖只读节点（先做，约 1–1.5 天）**

- 把商品、订单、售后、知识的只读查询接入统一 runtime 或共享策略。
- `ToolPolicy` 增加 `fallback_chain`、`stale_allowed`。
- 商品允许 30s 进程内缓存并标记 `stale=true`；订单、售后禁止 stale。
- 统一 `tool_evidence`：`tool / status / source / fallback_level / stale / latency_ms`。
- 失败时使用 `TOOL_UNAVAILABLE_REPLY`，不再把工具失败伪装成知识没找到。

**A3.2 RAG 降级链（随后做，约 0.5–1 天）**

- rerank 失败 → 跳过重排，`retrieval_mode=vector_only`。
- embedding / vector recall 失败 → FAQ curated 缓存，再退 2-gram `ILIKE` 关键词召回。
- 仍无结果 → `knowledge_gap` + 安全话术 + 工单。
- 开关：`TOOL_FALLBACK_ENABLED`、`RAG_DEGRADED_RECALL_ENABLED`。

### 不做

- 不做订单/售后 stale cache。
- 不做工具失败后编造事实。
- 不引入 Redis；先做进程内缓存，多 worker 后再迁共享缓存。
- 写操作仍走确定性事务，不进入只读 runtime。

### 验收

- 注入 catalog 超时：`status=degraded`、`source=cache`、`stale=true`，回答提示以下单页为准。
- 注入 rerank 超时：知识回答仍返回，标记 `vector_only`。
- 注入订单/售后超时：返回 `TOOL_UNAVAILABLE_REPLY`，绝不返回旧订单/售后事实。
- 连续失败达到阈值后熔断，冷却后半开恢复。
- 每个失败路径都有 `tool_evidence`，管理端可审计。

## A4. Turn 2A：回合幂等与断线重试

### 现状

- 没有 `chat_turns` 表，没有 `Idempotency-Key`，没有回合级状态。
- 客户端断开时 `stream_message` 会取消当前 task；没有 `done` 时前端只能回拉历史、提示重试。
- 重发可能重复写 user 消息，或让同一回合产生多条 assistant 消息。

### 建议范围（只做 2A）

- 新增 `chat_turns` 表：`id`、`conversation_id`、`user_message_id`、`assistant_message_id`、
  `client_request_id`、`status`、`intent`、`slots`、`attempt_no`、`error_code`、`lease_until`。
- `POST /messages/stream` 接受 `Idempotency-Key`。
- 同一 `client_request_id` 重试复用同一个 turn，不重复写 user 消息。
- 断线重试时用 `replace` 返回完整答案，不做 token 级回放。
- 服务重启把 `running` 标记为 `interrupted`，不假装续跑。
- 写操作/退换货写入只做幂等拒绝，不做自动续跑。

### 不做

- 不做 2B 的 `chat_turn_events`、`Last-Event-ID` 回放。
- 不做 token 级模型状态续写。
- 不做跨实例任务共享。

### 验收

- 同一 `Idempotency-Key` 重发两次：只有一条 user、一条 assistant。
- 生成中断后重试：回合能完成，前端不出现两条重复回答。
- 服务重启后未完成 turn 明确标记 `interrupted`。
- 新增迁移可 `alembic upgrade head`，旧表不受影响。
