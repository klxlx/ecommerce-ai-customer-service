# 未实现的优化方向

> 面向外部阅读的方向说明，不是任务清单，也不代表已排期。具体实现时再拆任务、定顺序。

## 当前基础

系统已经具备可演示的完整闭环：六层架构、对话主链路、人工接管、拍照退换货、FAQ 缓存和基础观测都已落地。剩余工作主要集中在三条主线：异常时是否稳、长会话是否记得住、失败后是否可解释。

下面只记录方向与判断，不展开到接口、字段和工时。

## 1. 模型失败：自动重试

继续完善统一的超时、重试、总预算和熔断策略，覆盖对话、向量化和重排。流式场景优先保证首 token 前可恢复；已经输出内容后不再续写，改为非流式重生成并整体替换气泡。目标是失败可恢复，但不让用户看到半截答案或重复回答。

## 2. 工具与检索：多级降级

商品、订单、售后、知识等只读查询统一走工具运行时，有明确的超时、重试、熔断和错误类型。检索侧按“重排 → 向量召回 → FAQ / 关键词”逐级回退；仍无结果时落到安全话术和工单。

订单、售后等强事实不能用旧缓存冒充当前结果；备用数据源只作为降级，不作为事实来源。

## 3. 任务中断：断点回复

以回合为单位记录状态和幂等键，断线或服务重启后能判断“未完成 / 已中断 / 可重试”，避免重复消息和重复回答。先做幂等与断点恢复，事件级回放作为后续增强；写操作仍保持确定性流程，不做自动续跑。

## 4. 上下文工程：摘要

长会话超过阈值后生成可审计摘要，作为独立上下文块注入，而不是继续膨胀原始历史。摘要需要能查看、能回滚，默认关闭，避免摘要本身成为新的不确定性来源。

## 5. 用户画像：可控的长期记忆

只记录用户显式确认的稳定事实，不跨会话推断敏感属性。默认关闭，可查看、可清除；先证明“长对话确实丢信息”再考虑扩大范围，不做全量记忆方案。

## 6. 可观测性与评测（建议补充）

把重试、降级、熔断、哨兵和工单等关键路径统一进 trace 与指标，并建立小规模失败样本回归集。需要能回答两个问题：这次降级有没有生效？回答是否仍然安全？没有这层，前三类兜底只能算“代码存在”，很难证明有效。

## 7. 安全、成本与部署（建议补充）

- **安全**：工具调用白名单、敏感字段脱敏、管理端操作审计，避免演示数据与真实密钥混用。
- **成本**：模型调用预算、缓存命中率和长会话成本上限，避免降级链本身带来额外开销。
- **部署**：真实网关下的 SSE 长连接、容器实机构建、数据库备份恢复和多 worker 缓存一致性，至少做一次故障演练。
