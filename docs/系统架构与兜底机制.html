三类兜底

只写代码里真实存在的机制

缺口即优化输入

模型失败 → 自动重试

部分有

非流式有，流式没有。 统一重试 / 熔断框架，预算按 provider 配置。

  • 有：complete（chat / embedding / rerank）走 execute_with_resilience
  • 默认重试 2 次（共 3 次尝试），固定 0.5s 退避
  • chat 30s/次、60s 总预算；embedding 20s/60s；rerank 15s/30s
  • 可重试：timeout / connection / rate_limit；auth / invalid / quota 不重试
  • 连续 3 次最终失败 → 熔断 30s
  • 没有：流式 stream 自动重试；只有 30s 空闲超时 + 60s 总预算
  • chat 最终失败 → PROVIDER_FAILURE_ANSWER + 转人工工单

tool 故障 → 服务降级

有基础降级

工具失败不硬编事实，统一降到安全话术与人工。

  • 知识检索异常 / 无结果 / 上下文不足 → knowledge_gap + 安全话术 + 工单
  • 商品、订单、售后查询异常 → KNOWLEDGE_GAP_REPLY + 转人工
  • 售后状态区分 query_error / no_records / not_available
  • FAQ 缓存异常 → 跳过缓存继续主链路；哨兵异常 → fail open
  • 没有：备用数据源、静态知识兜底、工具级重试 / 熔断

任务中断 → 断点回复

没有

没有 checkpoint、断点续跑或自动续答。

  • 现有：SSE 心跳保活、知识回答先缓冲再输出、replace 覆盖气泡
  • 前端未收到 done → “流式响应中断，请重试”；回拉历史后由用户重发
  • 槽位续接（补订单号 / 商品名）只恢复澄清意图，不是任务断点恢复
当前缺口：流式模型调用无重试、工具无备用源、任务无断点。这三项直接进入下一支线“系统优化”。
